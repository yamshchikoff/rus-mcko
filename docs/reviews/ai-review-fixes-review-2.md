## 3. Позитивные находки

### 3.1. Чистый common.py

Модуль содержит ровно то, что нужно: константы, `make_tools()`, `execute_tools()`. Без лишних абстракций. Оба потребителя (`server.py`, `review.py`) импортируют идентичный набор.

### 3.2. Корректная плюрализация

Алгоритм `pluralizeScore` в JS и `pluralize_score_py` в тестах идентичны. Покрыты все граничные случаи: 1, 2-4, 5+, 11-14, 21-24, 111-114. Правильная реализация через `mod10`/`mod100` — стандартный подход для русского языка.

### 3.3. Защита от stale-уведомлений

`notifyModelOfReview` теперь пушит нотификацию в `chatMessages` только после успешного `fetch` — если API возвращает ошибку, история чата не засоряется. Это корректное поведение.

### 3.4. Валидация variantNum

Проверка `isinstance(variant_num, int)` + диапазон 1..15 — достаточная защита. Если значение невалидное, зануляется (модель увидит `variant_num=0` в форматированной строке как «Вариант 0» — безвредно).

## 4. Замечания

### 4.1. Нелинейный UX в notifyModelOfReview (лёгкое)

**Файл:** `src/frontend/legacy/index.html:316-328`

Порядок операций после успешного fetch:
```javascript
appendAssistantMessage(textBlocks);    // 1. ответ модели
chatMessages.push(notification);       // 2. уведомление в историю
// ... рендер системного div ...       // 3. визуальное сообщение
```

Системное сообщение «Работа проверена. Результаты под заданиями →» появляется ПОСЛЕ ответа репетитора. Для пользователя это выглядит нелогично: репетитор уже комментирует прогресс, а только потом появляется плашка о завершении проверки. Стоит поменять порядок: сначала уведомление, потом ответ модели.

### 4.2. Дублирование тестов make_tools/execute_tools (лёгкое)

`tests/tutor/test_server.py` уже содержит `TestMakeTools` и `TestExecuteTools` (тестируют через импорт из server). `tests/tutor/test_common.py` содержит аналогичные тесты (тестируют common напрямую). Это не баг — разные уровни тестирования (unit vs integration), но при рефакторинге server.py тесты в test_server.py стали косвенно тестировать common.py. Можно рассмотреть удаление дублирующих тестов из test_server.py, оставив там только интеграционные.

### 4.3. `compact_history` на одном сообщении (лёгкое, п. 5.2 из ревью #1)

`src/tutor/review.py:220` — `compact_history(messages)` вызывается на списке из одного сообщения в первом проходе tool-use цикла. Не исправлено и не требует исправления — операция дешёвая, код корректен.
