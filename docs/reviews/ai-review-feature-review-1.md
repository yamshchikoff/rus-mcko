## 2. Критические замечания

### 2.1. Бракованный clamping баллов при отсутствующем `max_score`

**Файл:** `src/tutor/review.py:164-168`

```python
max_s = r.get("max_score", 0)
if r.get("score", 0) > max_s:
    r["score"] = max_s
```

Если модель не включила `max_score` в ответ (вернулся 0 по умолчанию), а `score` > 0 — балл зажимается до 0. Ученик получает 0 баллов за правильный ответ. Пример: модель вернула `{"issue": 1, "score": 3}` без `max_score` → в результате `score = 0`.

**Исправление:** добавить проверку `if max_s > 0` перед clamping'ом:

```python
max_s = r.get("max_score", 0)
if max_s > 0 and r.get("score", 0) > max_s:
    r["score"] = max_s
```

## 3. Серьёзные замечания

### 3.1. Дублирование кода: `execute_tools`, константы, инструменты

**Рекомендация:** вынести общие компоненты в отдельный модуль (`src/tutor/common.py` или `src/tutor/tool_executor.py`) на фазе REFACTOR. Константы определить в одном месте; `execute_tools` и `_toc`/`_fmt_entry` использовать из общего модуля.

Методология проекта требует цикл RED → GREEN → REFACTOR с отдельным коммитом для каждой субфазы. После RED (`e25bc37`) и двух GREEN (`742312d`, `c1840d5`) фаза REFACTOR не выполнена. Дублирование кода (п. 3.1) — прямая цель для REFACTOR'а.

### 3.3. Отсутствие документа спецификации

Согласно CLAUDE.md: «требования фиксируются в документе спецификации и сохраняются в директории `docs/specs/`». Спецификации для ИИ-проверки нет. Реализация есть, тесты есть, но формальных требований в виде документа не зафиксировано — непонятно, что считать «соответствием ожиданиям» кроме тестов.

## 4. Замечания средней тяжести

### 4.1. Некорректная плюрализация баллов в русском языке

**Файл:** `src/frontend/legacy/index.html:364-368`

```javascript
function pluralizeScore(n) {
  if (n === 1) return '';
  if (n >= 2 && n <= 4) return 'а';
  return 'ов';
}
```

Неправильно для чисел 11–14: «11 балла» вместо «11 баллов». Также для 111–114. Это работает только для чисел, оканчивающихся на 2–4 (кроме 12–14). Правильная реализация должна смотреть на последние две цифры:

```javascript
function pluralizeScore(n) {
  const mod10 = n % 10;
  const mod100 = n % 100;
  if (mod10 === 1 && mod100 !== 11) return '';
  if (mod10 >= 2 && mod10 <= 4 && !(mod100 >= 12 && mod100 <= 14)) return 'а';
  return 'ов';
}
```

### 4.2. Расхождение таймаутов: фронтенд vs бэкенд

Фронтенд (`requestAIReview`) устанавливает таймаут 120 секунд. Бэкенд (`execute_review`) делает до 5 итераций tool-use, каждая с `timeout=60` секунд на HTTP-запрос к DeepSeek. В худшем случае: 5 × 60 = 300 секунд. Фронтенд прервёт запрос на 120-й секунде, показывая ошибку «Проверка заняла слишком много времени», в то время как сервер продолжит выполнять 3-ю, 4-ю и 5-ю итерации вхолостую.

**Рекомендация:** либо увеличить фронтенд-таймаут до 360 секунд, либо сократить `MAX_TOOL_ITERATIONS` в `review.py` до 2, либо передать в `execute_review` общий таймаут, который бы проверялся между итерациями.

### 4.3. Устаревшее уведомление в истории чата при ошибке

**Файл:** `src/frontend/legacy/index.html:275-280`

```javascript
const notification = {
  role: 'user',
  content: `[Система] Ученик только что завершил вариант ${vNum}...`,
};
chatMessages.push(notification);
```

Уведомление добавляется в `chatMessages` ДО fetch-запроса. Если `fetch` падает, уведомление остаётся в истории чата как пользовательское сообщение. При следующем взаимодействии с чатом модель получит это сообщение и ответит на него, хотя проверка не удалась.

**Исправление:** пушить уведомление только после успешного ответа или удалять его из `chatMessages` в блоке `catch`.

## 5. Лёгкие замечания

### 5.1. Отсутствие валидации `variantNum` на бэкенде

**Файл:** `src/tutor/server.py:323`

```python
variant_num = payload.get("variantNum", 0)
```

Значение не валидируется на тип (должно быть `int`) и диапазон (1–15). Не критично для безопасности, так как используется только в строке форматирования сообщения.

### 5.2. `compact_history` вызывается на одном сообщении в первом проходе review

**Файл:** `src/tutor/review.py:276`

`build_review_messages` возвращает список из одного user-сообщения. В первом проходе tool-use цикла `compact_history` вызывается на этом списке — операция практически бесплатная, но семантически избыточная. Это не баг, но читатель кода может задаться вопросом «а зачем?».

### 5.3. Класс `TestReviewEndpoint` использует реальный `HTTPServer`

**Файл:** `tests/tutor/test_review.py:354-369`

Интеграционный тест поднимает реальный HTTP-сервер в потоке. Это делает тест чувствительным к состоянию глобального `textbook_path` и замедляет его (~0.5–1с). Для трёх тестов это приемлемо, но при росте количества тестов стоит рассмотреть тестирование хендлера напрямую через `TutorHandler` без настоящего TCP-сокета.

### 5.4. Отсутствие теста на clamping при `max_score == 0`

Все тесты проходят, но ни один не покрывает кейс из п. 2.1: `max_score` отсутствует, `score > 0`, результат должен сохранить `score`, а не обнулить.
