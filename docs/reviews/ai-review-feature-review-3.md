## 3. Оставшиеся замечания

### 3.1. Отсутствие спецификации (серьёзное, переоткрыто из ревью #1)

**Файл:** `docs/specs/` — нет `ai-review.md`

Методология проекта требует: «требования фиксируются в документе спецификации и сохраняются в директории `docs/specs/`». Спецификация для ИИ-проверки отсутствует. Это было замечание 3.3 в ревью #1, закрыто не было.

Сейчас есть только:
- `vpr-integration.md` — общая спецификация интеграции ВПР, упоминает ИИ-репетитора в превью, но не описывает `/api/review`
- `textbook-tools.md` — спецификация инструментов учебника

**Рекомендация:** создать `docs/specs/ai-review.md` с формальным описанием: эндпоинт, формат запроса/ответа, алгоритм scoring, обработка ошибок, интеграция с прогрессом.

### 3.2. Двойная запись прогресса в `finishWork` (среднее)

**Файл:** `src/frontend/legacy/index.html:921-929`

```javascript
function finishWork() {
  // ...
  markVariantCompleted(currentVariant);   // 1. запись со стаб-баллами
  renderProgressTable();
  document.getElementById('progress-section').style.display = 'block';
  requestAIReview(currentVariant);         // 2. внутри — markVariantCompleted с AI-баллами
}
```

При завершении работы `markVariantCompleted` вызывается дважды:
1. Сразу — со стаб-баллами (stub scoring)
2. После ответа `/api/review` — с AI-баллами (перезаписывает)

Это не баг, но:
- Первая запись в localStorage — лишняя: она будет перезаписана через 10–60 секунд.
- Если `/api/review` упадёт — останутся стаб-баллы (что, возможно, even желаемое поведение).
- Но прогресс-таблица рендерится дважды: до и после AI-проверки. Ученик видит стаб-баллы, которые через несколько секунд сменяются AI-баллами — UX-дёрганье.

**Рекомендация:** либо убрать первый вызов `markVariantCompleted` (AI-проверка всё равно запишет баллы), либо при ошибке AI-проверки восстанавливать стаб-баллы.

### 3.3. Нелинейный UX в `notifyModelOfReview` (лёгкое, из ревью #2)

**Файл:** `src/frontend/legacy/index.html:309-319`

Порядок после успешного fetch:
```javascript
appendAssistantMessage(textBlocks);    // 1. ответ модели
chatMessages.push(notification);       // 2. уведомление в историю
// ... рендер системного div ...       // 3. «Работа проверена. Результаты под заданиями →»
```

Системное сообщение появляется ПОСЛЕ ответа репетитора, что визуально нелогично. Репетитор уже комментирует прогресс, а потом появляется плашка о завершении проверки.

**Рекомендация:** поменять порядок: сначала рендер уведомления, потом `appendAssistantMessage`.

### 3.4. Прогресс-контекст в `notifyModelOfReview` может быть неполным (лёгкое)

**Файл:** `src/frontend/legacy/index.html:296-297`

```javascript
progressContext: buildTutorContext(),
```

Вызывается повторно, но `buildTutorContext()` читает `loadProgress()` из localStorage. Между `markVariantCompleted` (выполненным в `requestAIReview`) и этим вызовом — `saveProgress` уже отработал, так что контекст актуален. Однако `buildTutorContext` делает полный проход по всем 15 вариантам, что O(n) и нормально. Замечание скорее о читаемости кода: контекст уже собирался в `requestAIReview` — можно передать или кешировать.

### 3.5. Этические гайдлайны дублированы в двух системных промптах (лёгкое)

**Файлы:** `src/tutor/system_prompt.py:14-21`, `src/tutor/review.py:36-41`

`REVIEW_SYSTEM_PROMPT` и `TUTOR_SYSTEM_PROMPT` содержат пересекающиеся блоки этики:
- «Не высмеивай ошибки»
- «Не сравнивай с другими»
- «Безопасный взрослый»
- «Ученик имеет право на ошибку»

При изменении этических гайдлайнов нужно править оба файла. Можно вынести общий блок в `system_prompt.py` и импортировать в `review.py`.

### 3.6. `showReviewError` заливает одинаковую ошибку во все 7 слотов (лёгкое)

**Файл:** `src/frontend/legacy/index.html:352-360`

При ошибке проверки все 7 review-блоков получают один и тот же текст ошибки. Визуально — 7 одинаковых оранжевых плашек. Для пользователя это выглядит как 7 ошибок, а не как одна.

**Рекомендация:** показывать одну плашку-баннер над всеми заданиями, а не 7 отдельных.

## 4. Позитивные находки

### 4.1. Чистая архитектура `common.py`

Модуль содержит ровно то, что разделяют `server.py` и `review.py`: константы, `make_tools()`, `execute_tools()`. Без лишних абстракций. С момента ревью #2 не раздулся.

### 4.2. Надёжный парсинг ответа модели

Три стратегии извлечения JSON (code fence → braces → raw) + валидация + clamping + defaults. Даже если модель вернёт текст с вкраплениями JSON — ответ будет извлечён. `parse_error` fallback позволяет фронтенду показать сырой текст, а не пустоту.

### 4.3. Корректная обработка граничных случаев

- `max_score` отсутствует → clamping пропускается (исправлено по ревью #1)
- `score < 0` → зажимается до 0
- Пустой ответ → мягкая обратная связь в промпте
- Частичный ответ модели (не все 7 заданий) → обрабатывается
- Пустой ответ API → `parse_error`

### 4.4. Прогресс-контекст в системном промпте ревью

Модель видит историю ученика при проверке каждого задания — это даёт контекст: «этот ученик систематически ошибается в причастных оборотах, стоит обратить особое внимание на задание К3».

### 4.5. Визуальный дизайн review-блоков

Три градации score-бейджа (high/mid/low) с цветовой индикацией, иконки перед разделами (`✓ ⚡ 📖`), ссылки на параграфы учебника. Понятно для школьника 13–14 лет.

### 4.6. Тестовое покрытие

- Системный промпт (6 тестов)
